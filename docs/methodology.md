# 공정한 비교와 결과 해석

## 1. 바꾸는 것은 하나만

A와 B의 차이는 **비교 대상(플러그인·스킬·MCP) 하나**여야 합니다. 나머지는 모두 같게 둡니다.

| 같게 둘 것 | 이 도구가 하는 일 | 사용자가 할 일 |
|---|---|---|
| 모델 | `experiment.json`의 `model`을 양쪽에 `--model`로 고정 | 실험 중에 `/model`로 바꾸지 않기 |
| 출발점 | 실행 전마다 작업 폴더를 `fixture\`로 초기화하고 자동 메모리도 지움 | 실습 원본을 측정 도중 바꾸지 않기. 대화형 재촬영 때도 "작업 폴더 초기화"를 켜기 |
| 지시문 | 같은 파일을 양쪽에 그대로 전달 | 대화형에서는 같은 문장을 붙여 넣기 |
| 권한 | 헤드리스는 같은 `--permission-mode` | 대화형에서는 확인 창에 같은 답 |
| MCP | A는 비어 있음, B는 `mcp-B.json`만 | 비교 대상이 아닌 서버를 B에 넣지 않기 |
| Claude Code 버전 | `conditions.json`에 기록 | 측정 도중 업데이트하지 않기 |

## 2. 반복 횟수

같은 지시문도 실행마다 결과가 달라집니다.

- **최소 3회, 영상에 숫자를 넣는다면 5회 이상**을 권장합니다.
- 평균과 함께 성공/전체 횟수를 같이 보여 주세요. "B가 평균 20% 빠르다"보다
  "5번 중 A는 3번, B는 5번 성공"이 더 정직한 비교일 때가 많습니다.
- 차이가 작으면(대략 10% 안쪽) 반복 횟수를 늘리기 전에는 "차이가 있다"고 말하지 않는 편이 안전합니다.
- **A/A 시험으로 잡음을 먼저 재세요**(`-Mode AA`). 같은 환경끼리도 비용·시간이 이만큼 달라진다는 기준이 생기고,
  보고서 판정 카드가 그보다 작은 차이를 "의미 없음"으로 처리합니다. 영상에서 "같은 환경끼리도 ±15%"를 먼저 보여 주면 신뢰도가 크게 오릅니다.
- 보고서의 **분포**(최소–최대)가 A와 B에서 많이 겹치면 평균 차이를 강조하지 마세요.

## 2-1. 판정 기준은 측정 전에

- `experiment.json`의 `decision`(품질 차이, 비용·시간 허용 증가, 대상 호출 비율)을 **측정 전에** 정하세요.
  결과를 본 뒤 기준을 바꾸면 보고서가 "판정 기준이 측정 뒤 바뀜"으로 표시합니다.
- 과제는 비교 대상이 **유리할 것**과 **상관없거나 불리할 것**을 섞으세요. 판정 카드는 과제별 판정을 함께 보여 주므로
  "어떤 작업에는 쓰고 어떤 작업에는 쓰지 말라"는 결론을 낼 수 있습니다.
- 상시 비용(첫 요청 컨텍스트 차이)은 대상을 쓰지 않는 작업에서도 매 세션 냅니다. 채택 결론과 함께 밝히세요.

## 3. 순서와 캐시

- 프롬프트 캐시 때문에 먼저 실행한 쪽보다 나중에 실행한 쪽이 비용이 덜 나올 수 있습니다.
  `run-headless.ps1`은 회차마다 A/B 순서를 바꿔 이 효과를 상쇄합니다.
- 대화형 비교에서는 거의 동시에 시작하세요.

## 4. 측정값 읽는 법

| 값 | 의미 | 주의 |
|---|---|---|
| `CostUSD` | Claude Code가 보고한 API 기준 비용 | 구독 요금제에서는 실제 청구액이 아닌 추정값. 상대 비교용 |
| `Turns` | 에이전트 순환 횟수 | 적을수록 좋다고 단정할 수 없음(검증을 더 했을 수도 있음) |
| `Seconds` | 전체 실행 시간 | 네트워크·서버 상태 영향이 큼 |
| `OutputTokens` | 모델이 생성한 토큰 | 스킬이 장황한 출력을 유도하는지 보기 좋음 |
| `CacheReadTokens` | 캐시에서 읽은 입력 토큰 | 스킬·플러그인이 컨텍스트를 얼마나 키우는지 간접 지표 |
| `TargetCalls` / 대상 호출 회차 | 비교 대상(B에만 로드된 스킬·에이전트·MCP)을 호출한 횟수와 그런 실행의 비율 | 0이면 B의 차이는 비교 대상 덕분이 아님. 먼저 확인할 값 |
| `FirstContextTokens` | 첫 요청에 들어간 입력 전체 | A/B 차이가 비교 대상의 상시 비용(쓰지 않아도 매 세션 냄) |
| `ChangedFiles` | 원본 대비 바뀐 파일 수 | 품질 지표가 아님. 범위를 벗어난 변경을 찾는 단서 |
| `IsError` / `Subtype` | 실행 실패 여부 | 예산 초과(`--max-budget-usd`)도 여기 나타남 |

## 5. 품질 판정

숫자보다 중요한 것은 "결과가 맞았는가"입니다. 지시문을 쓸 때 판정 기준을 미리 정해 두세요.

- **자동 판정 가능한 과제를 고르기**: 테스트 통과, 빌드 성공, 특정 출력 일치. 그 명령을 `experiment.json`의
  `check.command`에 적으면 반복 측정이 매 실행 뒤 자동으로 돌려 "확인 통과"로 기록합니다.
- **채점표 쓰기**: 사람이 판정해야 하면 항목을 미리 정합니다(예: 요구사항 충족 / 불필요한 변경 없음 / 설명 정확).
  "부분"의 기준도 미리 적어 두세요.
- **블라인드 판정**: 앱의 결과 화면에서 A/B를 가린 채 판정하고, 다 끝난 뒤에 "정체 공개"를 켭니다.
  확인 명령 결과와 변경 파일 이름은 보이므로, 그것만으로 쪽이 드러나는 과제라면 판정 전에 감안하세요.
  가장 흔한 노출은 **최종 응답 본문**입니다(예: B가 "superpowers 스킬로 테스트부터 작성했습니다"라고 씀).
  스킬 이름이 보이더라도 결과의 품질만 기준으로 판정하고, 그런 답안이 많았다면 메모에 남기세요.
- 판정 이유는 답안별 메모와 `NOTES.md`의 "관찰"에 남깁니다.

## 5-1. 비교 조건 동등성

- B 구성은 `b-config.ps1`(또는 앱)로 넣어 버전·커밋을 기록하세요. 손으로 넣은 것은 "기록 없음"으로 남습니다.
- 측정 전에 `doctor.ps1 -Exp`의 "A/B 동등성"이 통과하는지 확인하세요. 계정 스킬 목록이 다르면 양쪽을 한 번씩
  대화형으로 실행해 동기화한 뒤 다시 점검합니다.
- 보고서에 "A/B 동등성 경고"가 있으면 그 측정은 영상의 근거로 쓰지 말고 다시 측정하는 편이 안전합니다.

## 6. 영상·자료로 만들 때

- **첫 장면에 환경 증명**: 양쪽 `/context`(또는 `/plugin`)를 보여 주고 "왼쪽은 기본, 오른쪽은 OO만 추가"라고 말합니다.
  반복 측정 보고서의 "실제 로드 확인(init)"·"대상 호출 회차"를 자막으로 붙이면 "정말 그 스킬이 일했다"는 근거가 됩니다.
- **녹화는 앱으로**: "세션 시작 때 녹화"를 켜고 시작하면 화면 녹화(mp4), 유튜브 챕터, 장면별 캡처, 시각이 붙은 터미널 기록이
  세션 기록 폴더에 모입니다([app.md 5-1절](app.md#5-1-녹화캡처표시영상-제작용)). 계정 이메일은 가려지지만 공개 전에 첫 화면을 한 번 확인하세요.
- **긴 작업은 빨리 감기**: 멈춤 표시(`markers.json`)로 "기다리는 구간"을 찾아 편집에서 배속하고, 시간 차이는 반복 측정 숫자로 말합니다.
- **기준 정의를 한 줄로**: "기본 = Claude Code + claude.ai 기본 스킬, 계정 플러그인·MCP 제외" 같은 정의를 자막이나 설명란에 넣습니다.
- **숫자는 반복 측정 결과로**: 화면 비교는 장면 연출용으로, 비교표는 `REPORT.md` 값으로 씁니다. 회차 수를 함께 밝힙니다.
- **조건 공개**: 모델, Claude Code 버전, 권한 모드, 측정 날짜를 설명란에 적습니다(`conditions.json`에 모두 있음).
- **비교 대상 출처**: 플러그인·스킬의 저장소 주소와 버전(커밋)을 설명란에 적습니다.
- **편향 주의**: 비교 대상에 유리한 과제만 고르지 말고, 불리할 수 있는 과제도 하나 넣으면 신뢰도가 올라갑니다.
